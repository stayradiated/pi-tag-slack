# Follow-up Issues Implementation Plan

## Purpose

Resolve every item in [`docs/ISSUES.md`](./ISSUES.md) and leave `@stayradiated/pi-tag-slack@0.1.0` ready for release.

This plan records the implementation decisions agreed during design review. It is intended to be executable by an engineer without reopening those decisions.

## Agreed decisions

- Implement in dependency order rather than issue-number order.
- Refactor the database lifecycle once for both Issues 1 and 4.
- `initDb()` accepts an explicit database path while retaining `config.dbPath` as the normal default.
- Opening a different path while the module database is already open is an error; it must never silently reuse the first database.
- A failed initialization closes its SQLite connection and resets all module state.
- Setup does not delete or restore `config.env` if database bootstrap fails. It reports failure, closes the database, and does not claim success.
- `PI_TAG_SLACK_CONFIG` changes only the config file location. Generated storage paths remain the documented platform defaults.
- Ambient `DB_PATH` and `SESSIONS_DIR` values do not determine the paths generated by setup.
- Dotenv serialization chooses a delimiter that round-trips through the installed `dotenv` parser. It does not use shell-style quote or backslash escaping.
- Values that cannot be represented exactly by `dotenv` must be rejected rather than corrupted.
- Add focused dependency-injection seams for inbound messages and claimed queue-row execution. Do not mock all of Bolt or expose `_test` internals.
- Reject duplicate singleton CLI options consistently. Only `send --file` remains repeatable.
- A value-taking option followed by any `--...` token is treated as missing its value.
- The default text trigger is `pi-tag-slack`. The Slack slash command remains `/pi`.
- The canonical launchd identifier is `com.stayradiated.pi-tag-slack`.

## Out of scope

- Supporting or migrating pre-release database schemas.
- Adding a CLI framework.
- Broadly reorganizing Slack, queue, or database modules beyond the seams needed for correctness and direct tests.
- Relocating data beside a custom `PI_TAG_SLACK_CONFIG` file.
- Adding legacy binary, path, or daemon-name aliases.

## Batch 1: Database lifecycle and schema baseline

Covers Issues 1 and 4 infrastructure.

### 1.1 Make database initialization explicit and failure-safe

Update `src/db.ts`:

- Change the API conceptually to:

  ```ts
  initDb(dbPath: string = config.dbPath): void
  ```

- Initialize schema through a local candidate `Database` connection. Do not publish that connection as the module singleton and do not set `dbOpen = true` until all of the following succeed:
  - Parent directory creation.
  - Opening SQLite.
  - Required pragmas.
  - Reading and validating `PRAGMA user_version`.
  - Detecting unsupported version-0 application schemas.
  - Creating the version-1 baseline schema when appropriate.
  - Setting `PRAGMA user_version = 1`.
- If any operation fails:
  - Close the candidate connection if it was opened.
  - Reset `dbOpen`, the active path, and any connection state.
  - Rethrow the original error.
- Track the active database path.
  - Calling `initDb()` again for the same path may remain idempotent.
  - Calling it for a different path while open must throw a clear error.
- Make `closeDb()` reset state in a `finally` block, including when `Database#close()` throws.
- Log the explicit active path rather than relying on `config.dbPath`.
- Preserve support for `:memory:` in tests.

### 1.2 Replace skipped migration suites

Delete the two `describe.skip()` migration suites from `test/db-cwd.test.ts`. They test unsupported pre-release migrations and must not be converted into active migration tests.

Add a focused schema suite, preferably `test/db-schema.test.ts`, using temporary real SQLite files. Cover:

1. A new database is created successfully.
2. Every final table has the complete expected columns:
   - `channels`
   - `message_queue`
   - `message_log`
   - `scheduled_tasks`
   - `trusted_users`
3. Required indexes exist.
4. `PRAGMA user_version` is exactly `1`.
5. A valid version-1 database can be closed and reopened.
6. A version-0 database containing any application table is rejected as a pre-release schema.
7. A schema with `user_version > 1` is rejected.
8. After either rejection, initialization can succeed after the invalid file is closed and replaced.
9. A failed initialization does not cause a later call to return early as if a database were open.
10. Opening a second, different path while one database is open fails explicitly.

Use `better-sqlite3` directly for schema inspection and malformed database fixtures. Always close fixture connections in `finally` blocks.

### Batch 1 completion criteria

- No skipped schema tests remain.
- Initialization failure cannot leave a stale connection or `dbOpen` state.
- Explicit-path behavior is covered before setup begins using it.

## Batch 2: Setup paths, trust bootstrap, and dotenv serialization

Covers Issues 1 and 2 plus the setup portions of Issue 3.

### 2.1 Calculate one intended storage configuration

Update `src/cli/setup.ts`:

- Calculate storage paths once during `runSetup()`:

  ```text
  dataDir     = defaultDataDir()
  sessionsDir = <dataDir>/sessions
  dbPath      = <dataDir>/gateway.db
  ```

- Do not derive these values from ambient `DB_PATH` or `SESSIONS_DIR`.
- `PI_TAG_SLACK_CONFIG` controls only `configPath`.
- Use the same local `sessionsDir` and `dbPath` values for:
  - Directory creation.
  - `buildConfigFile()`.
  - Trust bootstrap.
  - The setup summary.
- Avoid re-importing `config.ts` to discover the new values. ESM caching means a generated file will not refresh an already-loaded config singleton.
- Bootstrap trust with the explicit path:

  ```ts
  try {
    initDb(dbPath);
    addTrustedUser(trustedUserId);
  } finally {
    closeDb();
  }
  ```

  The `finally` must also run when initialization or insertion fails.

- Do not print setup success, install a daemon, or print the completion outro after bootstrap failure.
- Keep the newly written config on failure. Do not attempt cross-file rollback or restore an overwritten config.

### 2.2 Guarantee config permissions

- Create new config files with mode `0600` directly where supported.
- Explicitly `chmod` after writing so overwriting a pre-existing file also ends at `0600` regardless of its previous mode or process umask.
- Add POSIX tests for both new and overwritten files.

### 2.3 Implement an exact dotenv serializer

Update `serializeDotenvValue()` in `src/cli/setup.ts`:

- Continue rejecting NUL, carriage return, and newline characters.
- Do not emit `\"` or doubled backslashes on the assumption that `dotenv` reverses them; it does not.
- Generate a representation that the installed `dotenv@17.4.2` parser returns exactly:
  1. Prefer backtick quoting when the input contains no backtick. Backtick-quoted dotenv values preserve spaces, `#`, single and double quotes, backslashes, and literal `\n`/`\r` sequences.
  2. If needed, try single quotes when the input contains no single quote.
  3. Use double quotes only when both the delimiter and dotenv's `\n`/`\r` expansion rules are safe for that input.
  4. Use an unquoted representation only when parsing cannot trim it or treat part of it as a comment.
  5. If no exact representation exists, throw a clear representability error instead of changing the value.
- The implementation may construct candidate encodings and verify their known parser semantics. Keep production behavior deterministic.
- Introduce one assignment helper so **every** generated assignment passes through `serializeDotenvValue()`, including constants such as `PI_BIN`, empty strings, numeric defaults, policy defaults, and logging defaults.

Required invariant for every non-throwing input:

```ts
parse(`VALUE=${serializeDotenvValue(input)}`).VALUE === input;
```

### 2.4 Add serializer tests

Expand `test/setup.test.ts` with table-driven round-trip cases for:

- Empty string.
- Leading, trailing, and embedded spaces.
- `#` at the beginning, middle, and end.
- Double quotes.
- Single quotes.
- Backslashes.
- Literal two-character `\n` and `\r` sequences.
- Combinations of spaces, `#`, both quote types, and backslashes.
- Backticks and delimiter fallback behavior.
- Any deliberately unrepresentable value, asserting an explicit error.

Add injection rejection tests for:

- NUL.
- Carriage return.
- Newline.

Parse a complete `buildConfigFile()` result with `dotenv.parse()` and assert every supplied value and every generated default is recovered exactly.

### 2.5 Add setup-path integration coverage

Add a non-interactive integration test, preferably in `test/trust-startup.test.ts`. Run setup in a fresh process so config-module caching cannot hide the real startup behavior.

Test environment:

- Temporary `HOME`.
- Temporary `PI_TAG_SLACK_CONFIG` path.
- Ambient `DB_PATH` pointing to a different, unintended temporary path.
- Valid placeholder token shapes (`xoxb-...` and `xapp-...`).
- `PI_TAG_SLACK_TRUSTED_USER_ID` set to a valid uppercase ID.
- Non-interactive stdin/stdout.

Assertions:

1. Setup succeeds.
2. Generated config mode is `0600`.
3. `PI_TAG_SLACK_TRUSTED_USER_ID` is not written to the file.
4. Parsing generated config yields the platform-default temporary-home `SESSIONS_DIR` and `DB_PATH`.
5. The trusted user exists in that generated `DB_PATH`.
6. The ambient unintended `DB_PATH` was neither created nor bootstrapped.
7. A second normal process, with `DB_PATH` and the bootstrap-user environment variable removed, loads the generated config and sees the trusted user. This may invoke `trust list` or a small normal startup/preflight seam; it must exercise a fresh config import.
8. Setup closes its database on both success and forced failure, allowing a subsequent open/retry.

### Batch 2 completion criteria

- Generated `DB_PATH` always matches the bootstrapped database.
- Setup writes and initializes only one intended database.
- Every generated dotenv assignment round-trips exactly.
- Setup secrets are mode `0600`, including after overwrite.

## Batch 3: Direct trust-boundary tests and focused seams

Covers the remaining work in Issue 3.

### 3.1 Database trust tests

Add `test/trust-db.test.ts` backed by a fresh real SQLite database for each test.

Cover:

- Exact acceptance of uppercase `U...` and `W...` IDs.
- Rejection of lowercase IDs, display names, `<@mention>` syntax, surrounding whitespace, embedded whitespace, punctuation, and invalid prefixes.
- Idempotent insertion and clear boolean return values.
- Stable ordering by creation time and user ID.
- Successful removal when more than one trusted user exists.
- Refusal to remove the final trusted user.
- Atomic removal of the user and deletion of only that user's `pending` rows.
- Preservation of other users' pending rows.
- Preservation of the revoked user's `processing` rows during direct removal.
- Startup recovery resetting all `processing` rows to `pending` before authorization cleanup.
- Startup recovery marking recovered and existing unauthorized pending rows `failed` with `processed_at` set.
- Trusted rows remaining pending.
- `sender === 'scheduler'` remaining authorized.

Where atomicity is asserted, inspect final database state rather than only return values.

### 3.2 Inbound message handler seam

Refactor `src/slack/client.ts` minimally:

- Extract inbound handling into a callable exported handler or handler factory, for example `createInboundMessageHandler(context, deps)`.
- Pass bot/team identity and relevant policy/config values explicitly rather than requiring tests to mutate module globals.
- Inject the side-effecting operations needed to observe the boundary, including:
  - Trust lookup.
  - User lookup.
  - Conversation lookup.
  - Existing-channel lookup.
  - DM/channel registration.
  - Attachment selection/processing.
  - Queue insertion.
  - Registration notice/Slack response.
- Keep production Bolt registration thin: construct production dependencies and delegate to the extracted handler.
- Keep bot/subtype filtering before authorization as appropriate, but ensure authorization happens immediately after confirming a real non-bot user and before every lookup or mutation listed above.
- Do not export an object named `_test` and do not mock the entire Bolt implementation.

Add `test/slack-auth.test.ts` message cases:

- An untrusted valid user returns silently.
- No user lookup, conversation lookup, registration, attachment processing, enqueue, notice, or Slack response occurs.
- A trusted control follows normal handling and reaches the expected enqueue/registration path.
- Include enough DM and channel context to prove the trust check precedes both policy branches.

### 3.3 Slash command and Block Kit action tests

Test `registerCommands()` using a small fake `App` that captures callbacks registered through `command()` and `action()`.

A narrow injectable dependency object may be added to `registerCommands()` if needed to observe lookups and mutations; production defaults must remain the existing implementations.

Slash command cases:

- Untrusted command calls `ack()` exactly as required.
- It does not call `respond()`.
- It performs no channel lookup, model lookup, queue mutation, session mutation, or registration.
- Trusted control proceeds to the selected command behavior.
- Authorization uses `command.user_id`.

Block action cases:

- Untrusted action calls `ack()`.
- It does not call `respond()` or execute the registered action callback.
- It performs no channel lookup or mutation.
- Trusted control proceeds normally.
- Use differing opener/actor identities in a fixture and prove authorization uses `body.user.id`, the acting user.

Exercise every registered panel action, preferably through table-driven tests, so no action can omit the shared guard.

### 3.4 Claimed queue-row execution seam

Refactor `src/agent/queue.ts` minimally:

- Extract claimed-row execution into a normal callable function with injected side-effect operations, or accept an injected dependency bundle in the existing worker.
- Keep the production polling and dispatch path thin and behaviorally unchanged.
- The authorization check must remain after claim and before:
  - Channel lookup if it can trigger external behavior.
  - Message logging.
  - Busy reaction add/remove.
  - `invokeAgent()`.
  - Slack response.
- Unauthorized execution marks the row failed and may emit only a local debug log containing identifiers, never message content.

Queue tests must cover:

1. Claim a row while its sender is trusted, revoke the sender, then execute the claimed row through the seam.
2. The row becomes failed.
3. No agent invocation occurs.
4. No busy reaction is added or removed.
5. No Slack response occurs.
6. No user or assistant message-log row is written.
7. A trusted control executes normally.
8. A claimed scheduler row executes normally.
9. Startup recovery behavior from section 3.1 remains consistent with execution-time authorization.

Use real SQLite for queue state and injected spies for agent/Slack side effects.

### 3.5 Startup trust preflight tests

Add the smallest meaningful startup seam needed to test the trust-list gate without connecting to Slack. It may be a focused preflight function called by `startGateway()`.

Cover:

- Empty trust list rejects startup with:

  ```text
  No trusted Slack users configured. Run: pi-tag-slack trust add <user-id>
  ```

- The database is closed after rejection.
- Adding a trusted user allows startup to pass the trust preflight and reach the next injected startup operation.
- Do not make a real Slack network connection in tests.

### Batch 3 completion criteria

- Every user-initiated Slack entry point has trusted and untrusted controls.
- Negative tests assert absence of side effects, not merely a return value.
- Crash recovery cannot execute work from a revoked user.
- The scheduler exception is directly tested in recovery and execution.

## Batch 4: Strict CLI validation

Covers Issue 5.

### 4.1 Validate thread timestamps locally

In `src/cli/index.ts`, validate `send --thread` against:

```regex
^\d+\.\d+$
```

Perform this check before dynamically importing or calling Slack send code. Add malformed cases including missing fractional or integer parts, letters, whitespace, signs, and extra dots. Assert `sendFilesToSlack()` is never called.

### 4.2 Preserve trusted user input exactly

In `src/cli/setup.ts`:

- Remove `.trim()` from `PI_TAG_SLACK_TRUSTED_USER_ID` ingestion.
- Remove `.trim()` from accepted interactive trust input.
- Validation may use trimming only to decide whether a prompt is visually empty, but the value passed to `validateTrustedUserId()` must be exactly what the user supplied.
- Add environment and interactive regression tests proving surrounding whitespace is rejected.

Do not change token trimming as part of this task.

### 4.3 Normalize channel IDs before deriving defaults

In register parsing:

- Normalize and validate the channel argument first with the shared Slack JID normalization logic.
- Derive the default folder from the raw normalized Slack ID, not the original argument.
- Ensure both forms produce identical results:

  ```text
  C0123456789    -> jid sl:C0123456789, folder ch_C0123456789
  sl:C0123456789 -> jid sl:C0123456789, folder ch_C0123456789
  ```

- Add a regression test that registers one form, then re-registers using the other form without `--folder`, and proves the folder is unchanged.

Avoid validating or deriving a folder such as `ch_sl:C...`.

### 4.4 Enforce strict option parsing

Keep the hand-written parser, but make its rules consistent:

- Value-taking options must have a following token.
- A following token beginning with `--` is not a value; report the command's documented usage error.
- Reject duplicate singleton options:
  - `send`: `--channel`, `--thread`, `--text`.
  - `task add`: `--name`, `--schedule`, `--channel`, `--prompt`, `--once`.
  - `register`: `--folder`, `--cwd`, `--no-trigger`, `--main`.
  - `archive cleanup`: `--dry-run`.
- `send --file` is the only intentionally repeatable option.
- Unknown options remain errors.
- Do not add `--option=value` syntax or a CLI framework for this release.

Add table-driven malformed-input tests for every option-taking command. Include:

- Missing final value.
- Next recognized flag consumed as a value.
- Next unknown `--...` token consumed as a value.
- Duplicate singleton options.
- Repeated `--file` success control.

Ensure validation occurs before database opening, scheduler parsing, filesystem mutation, or Slack calls wherever practical.

### Batch 4 completion criteria

- Invalid thread timestamps fail without network access.
- Trusted IDs are validated exactly as supplied.
- Bare and `sl:`-prefixed channel IDs have identical identity and folder behavior.
- Missing and duplicate singleton options always fail with usage errors.
